Five configurations, and why each rule type was chosen

How overlapping rules are resolved

A configuration fires when any of its rules match. When rules from several configurations match the same page, the highest-scoring rule wins. Within one type, a longer and more specific value scores higher, so an exact host always beats a broad suffix and you can safely keep a company-wide default alongside per-host overrides.

TypeMatchesExampleScore
host-exactHostname equals the value exactlyapp.example.com1000 + len
ip-exactHostname is exactly this IP192.0.2.5900
ip-cidrHostname is an IPv4 in this subnet10.0.0.0/8800
url-regexFull URL against a regular expression^https?://.*/admin(/.*)?$700 + len
cookieCookie name, exact value, or containsdeploy=canary650 / 600 / 550 + len
host-suffixHostname and all its subdomainsexample.com500 + len

The three cookie scores correspond to the three cookie forms: name=value for an exact value, name~=fragment for a substring, and a bare name for presence alone. Each adds the length of the cookie name.

The five examples

01

Same-domain multi-environment

I have three environments sharing the same base domain:

  • https://app.example.com/ is production
  • https://test.app.example.com/ is test
  • https://staging.app.example.com/ is pre-production

I need distinct watermarks so I don't accidentally operate on the wrong one.

[
  {
    "name": "Production",
    "shortLabel": "PROD",
    "rules": [{ "type": "host-exact", "value": "app.example.com" }],
    "text": "Production - handle with care",
    "color": "#ef4444",
    "opacity": 0.15,
    "border": { "enabled": true, "color": "#ef4444", "width": 4 }
  },
  {
    "name": "Staging",
    "shortLabel": "SIM",
    "rules": [{ "type": "host-exact", "value": "staging.app.example.com" }],
    "text": "Staging",
    "color": "#f59e0b",
    "opacity": 0.15
  },
  {
    "name": "Test",
    "shortLabel": "TEST",
    "rules": [{ "type": "host-exact", "value": "test.app.example.com" }],
    "text": "Test",
    "color": "#10b981",
    "opacity": 0.15
  }
]

Why: Each hostname is distinct, so host-exact is the most precise rule. Production gets red plus an inset border, the loudest combination. Pre-production is amber, test is green.

02

VPN internal admin over IP

Our admin panel is only accessible over the office VPN at https://192.0.2.5/. There is no domain, just the IP. I want a purple watermark saying "Admin — Restricted".

[
  {
    "name": "Admin Console",
    "shortLabel": "ADMIN",
    "rules": [{ "type": "ip-exact", "value": "192.0.2.5" }],
    "text": "Admin — Restricted",
    "color": "#8b5cf6",
    "opacity": 0.18,
    "border": { "enabled": true, "color": "#8b5cf6", "width": 3 }
  }
]

Why: The browser hostname is literally 192.0.2.5, so ip-exact is the right rule — no domain rule could ever match here. The border is on to reinforce the restricted feel.

03

An entire internal subnet

Everything on our internal network 10.0.0.0/8 should get an "INTERNAL" watermark. External sites should not.

[
  {
    "name": "Internal",
    "shortLabel": "INT",
    "rules": [{ "type": "ip-cidr", "value": "10.0.0.0/8" }],
    "text": "INTERNAL NETWORK",
    "color": "#6366f1",
    "opacity": 0.12,
    "rotation": -25
  }
]

Why: 10.0.0.0/8 is a Class A private subnet, about 16 million addresses, covered by one rule. It matches only when the hostname is a raw IPv4 in that range, which is the normal case for internal-only tools.

04

Path-based admin routing on production

On our production site app.example.com the main app is fine, but I want a big red DANGER watermark on any URL starting with /admin. Regular pages should have no watermark.

[
  {
    "name": "Production Admin",
    "shortLabel": "ADM",
    "rules": [
      { "type": "url-regex", "value": "^https://app\\.example\\.com/admin(/.*)?$" }
    ],
    "text": "DANGER — production admin page\nEditing live data",
    "color": "#dc2626",
    "opacity": 0.2,
    "fontSize": 28,
    "border": { "enabled": true, "color": "#dc2626", "width": 5 }
  }
]

Why: This is path-based, not host-based, and url-regex is the only type that inspects the full URL. The doubled backslashes are JSON escaping for the literal dots; the $ is the regex end anchor.

05

Cookie-driven canary environment

We have a canary deployment where the URL is the same as production (app.example.com) but the backend routes on a cookie deploy=canary. When I am on the canary I want an orange "CANARY" watermark.

[
  {
    "name": "Canary",
    "shortLabel": "CNRY",
    "rules": [{ "type": "cookie", "value": "deploy=canary" }],
    "text": "CANARY ENVIRONMENT",
    "color": "#f97316",
    "opacity": 0.15
  }
]

Why: Same URL, same host — the cookie is the only distinguisher, so no host or URL rule can help. deploy=canary matches the exact value; if the value varies, such as canary-v1 and canary-v2, use deploy~=canary to match on the substring instead.

Check a rule before you save it

The options page has a rule tester. Paste a URL, optionally paste a cookie string, and it reports which configuration would match and which rule did it. That turns every example above into something you can verify in seconds instead of trusting.

URL field
The full address you expect to be marked, for example https://test.app.example.com/orders. Host, IP, CIDR and regex rules are all evaluated against it.
Cookie field
Optional, and written the way the browser writes it: deploy=canary; sid=abc. Cookie rules need this to resolve, because the extension reads cookies from the page rather than through a permission.
Unsafe pattern guard
Regexes that are excessively long or structurally catastrophic are refused rather than run, so a bad pattern cannot freeze the pages you visit.
